# Investment Cadence is served behind a stable FeatureExtractor + CadenceModel interface

Investment Cadence is produced by two stable, separately testable pieces: a `FeatureExtractor` (Firm → an ordered, named feature vector) and a `CadenceModel` interface (`predict(features) -> {score 0..100, contributions, model_version}`). The MVP ships `ColdStartCadenceModel` (the PRD's labeled cold-start weights, with time-since-last-check modelled as a bucketed/piecewise transform rather than a single linear weight); a `LearnedCadenceModel` (logistic regression or monotonic GBM) implements the same interface later. A `ReadinessLabel` generator and a backtest harness exist from day one, since seeded deals are dated.

Why: ADR 0005 fixes Cadence as a calibrated prediction of an explicit label — interpretable, swappable, and falsifiable. Pinning the swap point at a shared feature vector plus a narrow model interface makes the move from cold-start to learned weights a config change, not a rewrite, and the explainability requirement (top contributing factors) is satisfied identically by both (weight×value for cold-start and logistic regression; monotonic contributions for a GBM). This structure is required because time-since-last-check is non-monotonic, so a single hand-set linear weight is provably wrong in one regime, and a score with no target variable cannot be tuned or trusted.

Considered options: (1) shared FeatureExtractor + model interface (chosen); (2) inline the cold-start formula in the scoring service (rejected: not swappable, hard to backtest); (3) ship a black-box model (rejected: violates explainability, ADR 0005). Consequence: Cadence becomes a monitored model with a validation cadence and drift checks, not a static formula. Status: accepted.
