# DataSource is an ingestion/refresh seam, not a query-time layer

The app is built entirely against a `DataSource` (LakeB2B-shaped: identity + verified contacts + firmographics) and a separate `DealSource` (behavioral deal/portfolio data), both Python Protocols returning typed Pydantic records. These adapters POPULATE and REFRESH a normalized Postgres store; the query engine, scoring, and UI read only from Postgres. Two implementations sit behind the seam: `SeedDataSource`/`SeedDealSource` (generated fixtures, used now) and `LakeB2BDataSource` (HTTP, stubbed until the live API contract is known). Deliverability verification is a provider behind the seam, reusing the `lakeb2b-email-verify` package; Role currency is a separate provider.

Why: the real LakeB2B Data API is the #1 open question and is not wired — no client exists in any sibling project, and LakeB2B supplies contacts + firmographics, not investor/deal data. Making the adapter an *ingestion* seam (rather than a query-time data source) means the live API drops in by swapping one implementation, with zero change to filters-first search, ranking, scoring, or UI, because all of those operate on the normalized store. A query-time adapter was rejected: filters-first complete recall (ADR 0004), per-stage check-size aggregation, recency-weighted sector profiles, and pgvector ranking all require a queryable relational store, not per-request fan-out to an external API.

Considered options: (1) ingestion/refresh seam over a normalized store (chosen); (2) query-time adapter the engine calls per request (rejected: breaks recall, aggregation, and ranking); (3) couple directly to a single assumed API shape (rejected: not swappable). Consequence: seed data and live data are identical from the app's perspective, so the seed generator is a first-class, permanent test fixture. Status: accepted.
